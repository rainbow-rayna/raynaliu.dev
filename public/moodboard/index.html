AI Moodboard

A weekly scrapbook that tags its own references.

Pin a screenshot to a day of the week and it comes back as a Polaroid, tagged with five to ten design terms Gemini reads off the image — the vocabulary you'd actually search by, like Brutalist, Modular Grid, or Muted Earth Tones. Everything is stored per ISO week, so paging back to last week finds it exactly as you left it.

Walkthrough

Record 45–75 seconds: dragging a screenshot in, the analysis running, the Polaroid landing with real tags, then paging back to a previous week. Export as MP4 (H.264), save as public/moodboard/walkthrough.mp4, delete this box, and uncomment the tag below.

The demo board is pre-populated with real analysis — the tags on it came back from Gemini, generated ahead of time rather than at page load. The video is there to show the step a pre-populated board can't: an image going in and vocabulary coming back out.

Decisions worth explaining

The model version is pinned, deliberately

It would have been easier to point at a -latest alias. I pinned an exact model instead, because the failure mode of a floating alias is genuinely nasty here: when it gets retired or overloaded, every upload silently falls back to placeholder tags. The app keeps working, nothing errors, and the only symptom is that the output quietly gets worse. A pinned version fails loudly instead.

The API key cannot reach the browser

Vite is never handed the .env file, and nothing in src/ talks to Google directly. The browser uploads bytes to this app's own Express route, and that route is what calls Gemini. There's no path by which the key ends up in a client bundle — not by convention, but structurally.

Zero-setup Postgres

Leave DATABASE_URL empty and the server runs PGlite — real Postgres compiled to WebAssembly, in-process, writing to a local directory. Same SQL, same Drizzle migrations, no install step. Set the variable and it switches to a real server with the same migration files. Cloning the repo and running it takes one command, which is the difference between a project people try and one they don't.

Every environment variable is optional. With none set the app still runs end to end — uploads work, and images come back with clearly-labelled fallback terms rather than an error. That makes the project trivial to clone and run, which is a different goal from demonstrating it well; see the note on seeding below.

The prompt

Asking a vision model to "describe this image" gets you prose about what's in the picture. That's useless for a reference library — you can't search it, and it doesn't match how designers actually think about what they're collecting. The prompt gives the model a role, a vocabulary space, and a shape for its answer.

ANALYSIS_PROMPT
You are a design critic building a visual reference library. Look at this image and name the design characteristics you can actually see. Return between 5 and 10 terms. Rules for each term: - Established design terminology only — the vocabulary a designer would search by. Draw across style movements (e.g. Brutalist, Swiss Style, Memphis, Bauhaus, Y2K, Skeuomorphic), layout (e.g. Modular Grid, Asymmetric Balance, Split Screen, Broken Grid), typography (e.g. Grotesque Sans, Variable Weight, Oversized Type, Tight Tracking), colour (e.g. Muted Earth Tones, Duotone, High Chroma Accent, Monochrome), and material or texture (e.g. Glassmorphism, Grain Overlay, Halftone, Soft Shadow). - 1 to 3 words. Title Case. No sentences, no explanations, no hashtags, no trailing punctuation. - Concrete and visible in this image. Do not guess at brand, purpose, or content you cannot see. - No duplicates and no near-synonyms of each other. Prefer specific over generic. - Order them most to least defining.

The five named categories do most of the work. Without them the model fixates on colour and misses structure entirely — you get ten shades of beige and nothing about the grid. Naming the axes forces coverage across them.

"Do not guess at brand, purpose, or content you cannot see" is there because the failure mode of a vision model on a screenshot is confident invention. It will happily tell you it's looking at a fintech landing page. That's not searchable design vocabulary, and it's frequently wrong.

Structured output, so the happy path is a parse

The request pins responseMimeType and a responseSchema, so Gemini is constrained to answer in a shape that can be parsed rather than scraped: 

{
  type: "OBJECT",
  properties: {
    terms: { type: "ARRAY", items: { type: "STRING" },
             minItems: 5, maxItems: 10 }
  },
  required: ["terms"]
}

The response still gets validated with Zod afterwards. A schema makes malformed output unlikely, not impossible — a model can still return fenced JSON, a short array, or nothing at all, and the network can fail outright.

The failure ladder

Requests time out at 25 seconds and retry once on 429, 500, 502, 503, and 504 — the statuses that mean busy, try again, as opposed to this request is wrong. Retrying a 400 just wastes time and quota.

Everything that still fails lands on the same floor: terms derived from what's knowable without a model — aspect ratio, resolution band, file type, file size — ending with Awaiting Analysis, and recorded in the database as a fallback rather than as analysis.

That honesty is also why the public demo is seeded rather than keyless. A visitor with no key would see Landscape Format · PNG Source · Medium File · Awaiting Analysis — which is a correct answer, faithfully labelled, and demonstrates nothing whatsoever about the thing the project is for.

What I'd change

  • Uploads are written to the local filesystem, which is fine on a laptop and wrong on a host that wipes its disk on every deploy. Object storage is the obvious fix and the reason the live demo needed work before it could ship.
  • Tags come back as free text, so Muted Earth Tones and Earthy Muted Palette are separate tags forever. Some normalisation pass would make the tag cluster far more useful.
